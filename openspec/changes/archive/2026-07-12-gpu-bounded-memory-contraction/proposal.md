## Why

The `v100-validation-pass` change (archived 2026-07-05) found that `use_gpu=True` is a no-op end to end: `ContractionEngine._find_path_cutensornet()` falls back to CPU `opt_einsum` path-finding, and `_compute_marginal()` — the routine every batch contraction goes through — always contracts the **full `2^n`-entry amplitude tensor** on host NumPy before slicing out the requested `2^b` batch marginal. All three simulator phases (Traditional, Unoptimized PTSBE, Optimized PTSBE) hard-code `ContractionEngine(..., use_gpu=False)`. This isn't a missing speed optimization: a dense `2^n` array has no physical realization anywhere near the paper's n=100-200 regime (confirmed empirically — a 20-shot Traditional run at n=26 was killed after 4+ minutes with resident memory past 12.9GB and still climbing). Reaching any paper-comparable scale requires genuine bounded-memory GPU contraction, capped at `2^b` (the batch size) regardless of `n`, for all three phases — not just the optimized one.

**This change now runs on a single NVIDIA H100 80GB (the paper's own hardware, GH100 architecture, driver 550.127.08)**, not the V100 the prior validation pass used. With the paper's exact GPU class available, the goal for this change is a full, honest reproduction of the paper's results (arXiv:2604.08467): implement real bounded-memory contraction, then run the paper's exact circuit grid (n∈{50,75,100,150,200}, g∈{200,...,1000}, 10 instances each) for both non-proportional (Fig. 3, target ~10⁸×) and proportional (Fig. 5, target ~10³×) PTSBE, plus the final-batch-size sweep (Fig. 4) and per-batch contraction-cost sweep (Fig. 7), against our own `TraditionalTrajectorySimulator` as the CUDA-Q-equivalent baseline (b=24, 1 hypersample — already how that class is specced, standing in for CUDA-Q per the existing `traditional-trajectory-simulator` spec, since the `cudaq` package itself is not part of this codebase's dependency surface).

## What Changes

- Replace `ContractionEngine._find_path_cutensornet()`'s stub with real cuTensorNet-backed path finding.
- Replace `_compute_marginal()`'s dense-statevector CPU reference implementation with bounded-memory GPU contraction via `cuquantum.tensornet.experimental.NetworkState`, so a batch contraction's peak memory scales with `2^b` (batch/final-batch size), not `2^n`.
- Wire prefix conditioning (fixing already-measured qubits from prior batches) through to the GPU contraction primitive, replacing the current "contract full tensor then slice" approach.
- Rework `ContractionPathCache` semantics: the cache currently stores only path *metadata* on the assumption that UPV's "fuse error operators, keep topology, reuse path" trick is enough. A real `NetworkState`-backed engine needs to reuse the underlying network *structure* across error sets (only tensor *values* differ after fusion) to preserve UPV's "path found once, reused for all E error sets" guarantee — this needs validating against what `cuquantum`'s API actually allows (see design.md and the spike task in tasks.md) and may change what the cache stores.
- Flip `use_gpu=True` as the default in the three simulator classes (`traditional.py`, `unoptimized_ptsbe.py`, `optimized_ptsbe.py`), each still able to fall back to the existing CPU path when CuPy/cuQuantum aren't installed (as today).
- Add a correctness regression: bitstring distributions from the new GPU path vs. the existing CPU dense path must match (same style as `tests/test_simulators.py::test_proportional_matches_traditional_distribution`) at a scale beyond n=26, where the old CPU path could not run at all.
- Align `benchmarks/circuit_generator.py` with the paper's exact circuit-generation spec (Sec. IV-B: gate set H/X/Y/Z/T/Rx single-qubit, CX/CY/CZ/CH/CRx two-qubit nearest-neighbor, 20% two-qubit gates, Pauli/depolarizing noise with probability ~U[0.02,0.2]) and `benchmarks/run_benchmark.py` with the paper's default hyperparameters (Sec. IV-C: PTSBE b=10, bf=28, 100 hypersamples, 1 shot/non-final batch; Traditional b=24, 1 hypersample) and metric definitions (Sec. IV-D: throughput excludes path-finding for PTSBE, geometric mean/std over instances, >80%/<80% success-rate markers for configs that hit contraction time/memory limits).
- Run the paper's full experimental grid on the H100 and produce the paper's key figures from real results: Fig. 3 (non-proportional speedup vs g, per n), Fig. 4 (throughput vs g vs bf), Fig. 5 (proportional speedup vs shot count, two configs), Fig. 6 (contraction time/shot, path-finding time, and their ratio vs g), Fig. 7 (per-batch contraction+sampling time vs batch size, n=100/g=600). Record real geometric-mean speedups against the paper's headline claims (~10⁸× non-proportional, ~10³× proportional) in `benchmarks/validation_notes.md`, honestly noting any regime where they diverge and why.

**Explicitly out of scope**: multi-GPU/multi-error-set parallelism (the paper itself only parallelizes across distinct error sets *between* GPUs, Sec. VI; this change stays single-GPU as the paper's headline numbers are single-GPU too), lightcone-based circuit simplification (explicitly flagged by the paper, Sec. VI, as future work), any change to the UPV/NBS sampling algorithms themselves (`error_sampling.py`, the branching/exhaustive-harvest logic in the simulator classes) beyond how they invoke the contraction engine, and literal `cudaq` package integration (the existing `TraditionalTrajectorySimulator` already stands in for CUDA-Q per its spec).

## Capabilities

### New Capabilities

- `paper-figure-reproduction`: analysis scripts that consume benchmark JSON output and reproduce the paper's Figs. 3-7 (speedup/throughput plots), run over the paper's exact (n, g) grid.

### Modified Capabilities

- `contraction-engine`: contraction path finding SHALL use real cuTensorNet (via `cuquantum.tensornet.experimental.NetworkState`, not a CPU `opt_einsum` fallback disguised as GPU), and batched/conditional marginal contraction SHALL execute with peak GPU memory bounded by `2^b` (the requested batch size) rather than `2^n`. The path cache's stored contract SHALL be updated to reflect what's actually reusable across error sets under the new backend (UPV reuse via in-place tensor operand updates on a persistent `NetworkState`, not per-error-set network rebuilding).
- `benchmarking-harness`: circuit generation SHALL use the paper's exact gate set and connectivity (not arbitrary Haar-random unitaries), default hyperparameters SHALL match the paper's Sec. IV-C values, and per-configuration pass/fail SHALL be tracked with the paper's >80%/<80% success-rate convention. Speedup aggregation SHALL use geometric mean/std (not arithmetic), matching the paper's Sec. IV-D metric definition.
